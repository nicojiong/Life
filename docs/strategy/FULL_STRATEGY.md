### 3. 十项优先发现

#### A01｜P0：死亡不是可靠的结算终点

`_on_action()` 先通过 `_advance_months(m)` 跳时；跳时可能进入 `_ending()` 并清档，但返回后仍执行收益、特殊效果和 `_save_game()`。战死经 `_die_young()` 进入结局，也可能返回外层继续存档。`ended` 又未进入存档。

源码支持的风险是“行动中途死亡后仍发奖”和“清档后重写普通存档”；实际表现需运行复现。应统一行动结果 `completed / interrupted / actor_died / world_ended`，死亡后立即终止当前命令，再生成独立人生档案。

证据：[`_on_action` 2970–3006](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L2970-L3006)、[`_advance_months` 3420–3443](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L3420-L3443)、[`_die_young` / `_ending` 3675–3686](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L3675-L3686)。

#### A02｜P0：存档不能完整恢复同一个世界

`_ready()` 先随机 `_init_identity()`，再 `_load_game()` 局部覆盖。`_state_dict()` 未完整保存 `father_trade`、`mother_temper`、当前 `women_rank`、`scenes_done`、`child_last`、`month_frac`、`time_scale`、NPC 状态、随机数状态等。

这使家庭属性可能来自新随机初始化；母亲当前职业可能丢失；节令与童年去重记录可能重置；模拟无法准确续接。应新增版本化 SaveEnvelope，区分游戏事实、人物状态和表现状态，提供迁移、校验、备份与原子写入。每个缺漏字段是否导致用户可见错误，要用专项往返用例确认。

证据：[`_ready` 272–278](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L272-L278)、[`_state_dict` / `_load_game` 301–411](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L301-L411)。

#### A03｜P0：死亡父母与旧档补全使用同一种“缺失”状态

`_parent_death()` 从 `pov_state` 删除死亡父母；`_load_game()` 看到缺少父亲或母亲，会按兼容旧档的逻辑重新生成，未区分死亡与旧版本缺字段。应以稳定 actor ID 和 `alive/death_record` 表示死亡，禁止用删除人物实体表达死亡。旧档迁移按 `schema_version` 执行，不能每次读档补生。

证据：[`_load_game` 391–397](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L391-L397)、[`_parent_death` 2246–2254](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L2246-L2254)。

#### A04｜P1：时间成本不一致，短行动可以即时刷值

地点行动只有 `months >= 6` 才推进月份；对话总推进 `months`；节令自行跳时；实时钟又独立推进。于是“歇三个月”可即时加健康，“看告示”可即时加学识，母亲“浆洗三个月”可即时加钱和手艺。`_strip_time()` 同时隐藏部分时间文案，让真实成本更难理解。

应选择唯一模拟时钟：长期收益必须消费时间或有限精力，查看与取消免费。地图走动可以保留表现时间，但不得与人生时间重复结算。长活动需要明确是否可中断及中途死亡如何处理。

证据：[`_on_action` 2987–2994](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L2987-L2994)、[对话推进 2212–2233](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L2212-L2233)、[浆洗与隐藏时间 1242–1254](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L1242-L1254)。

#### A05｜P1：NPC 好感依附画面，重建与换视角会清零

对话修改 `npcs[i]["att"]`，但 `_spawn_npcs()` 每次重新创建 `att:0`。切视角、重建场景、读档都会经过重新生成。当前记忆不能支撑十年后仍记得玩家的行为。

应由 WorldState 持有关系和记忆，场景只按 actor ID 展示。关系至少区分信任、亲近、恩怨和债务；重要经历保存事件 ID，不能只留一个总分。

证据：[`_switch_pov` 1132–1152](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L1132-L1152)、[`_spawn_npcs` 1885–1976](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L1885-L1976)、[态度修改 2224–2227](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L2224-L2227)。

#### A06｜P1：世界结算依赖当前控制谁

`_advance_months()` 给缓存人物年龄加一，但年关健康衰退、收入、事件、婚育里程碑主要操作当前视角的全局字段。婚姻、子女、父母存活数又由共享变量表示。非控制人物没有同等生命周期处理，另有主角 46 岁的固定丧亲剧情。

需要拆出 Actor、Household、World 三类状态，并让关键人物统一随时钟更新。主角一生模式默认只控制主角；父母引导由其资源、价值观和关系决定。保留父母视角时，观察行为不能改变世界规则。

证据：[视角字段 110–116](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L110-L116)、[年推进与年关 3427–3578](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L3427-L3578)。

#### A07｜P1：延迟因果固定在年龄，临时人物无法可靠恢复

借米说“秋后还”，实际催债只在 22 岁触发；22 岁以后借款没有相同后续。“宽限三个月”只设置 flag，并未创建三个月到期任务。媒人和债主生成标记被保存，临时 NPC 本身未保存，读档可能留下“已经生成、人物不在”的状态。

应采用 `event_instance + due_at + bindings + cause_id + status`，到期时重新校验双方存活、地点、债务和关系。晚年借款也应按借款日计算后果。婚育可提供年龄窗口，但不能把某岁必生子当通用世界规则。

证据：[借米 2369–2371](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L2369-L2371)、[还款与延期 3075–3081](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L3075-L3081)、[固定生成 3482–3489](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L3482-L3489)。

#### A08｜P1：时代与地域配置只部分消费

DB 固定读 `song.json`；出生年固定 1040–1044；时代 `timeline/start_year/end_year` 未用于世界推进。地点文字可为汴京或边地，但仍使用同一村庄与人物。现状不是“只差时代选择按钮”，而是缺少控制制度、职业、经济、事件、姓名和地点的 EraPack 边界。

先把北宋抽为完整配置包；第二时代用于验证通用引擎，不能只换显示文本。主角性别也应纳入出生身份和时代规则，避免扩展女性角色时沿用固定男性婚育文案。

证据：[DB 固定加载 30–40](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/core/db.gd#L30-L40)、[出生固定分支 962–983](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L962-L983)、[北宋配置](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/data/era/song.json)。

#### A09｜P1：内容标识已有接线错误，必须先建立校验

商人家庭配置 flag 是“商贾”，出生逻辑检查“商人”，该出身的父亲行当会落入默认“农”。NPC `lao_seng` 连续定义两次。应使用稳定机器 ID，展示名称另存；导入时校验唯一 ID、引用、枚举、年龄约束、时代范围和数值边界。

证据：[商贾配置](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/data/origins.json#L35-L45)、[商人分支 989–998](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L989-L998)、[重复老僧 1915–1916](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L1915-L1916)。

#### A10｜P2：结局和开发验证还不能衡量“独特人生”

墓志最高档依赖进士与声望，普通、独身人生容易得到“余无可书”。可以保留社会记载等级，同时增加个人愿望、亲密关系、实际影响和重要选择的独立叙述。结局必须引用真实事件，不凭空补写。

现有 debug 多为直接设状态、调用特殊效果并打印，缺少统一断言与失败退出码；截图证明某帧能显示，不能证明路线可达、存档正确或长期稳定。科举等调试会绕过正常行动前置条件，应另有从出生走正常接口的测试。

证据：[墓志评级 3766–3794](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L3766-L3794)、[科举调试 935–952](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/street/village_scene.gd#L935-L952)。

### 5. 调试与存档保护：先核实再运行

已有可复用入口包括 `village_save/load/years/exam/craft/trade/med/farm/mil/pov/father/mother/scenes/festival/epitaph`。它们可作为夹具素材，不能直接作为自动验收结论。`--shot=...` 在等待渲染后保存 PNG 并退出，也没有检查游戏规则。

**`--fresh` 的真实范围是四个文件：** `fusheng_save.json`、`fusheng_save_1.json`、`fusheng_save_2.json`、`fusheng_save_3.json`，位于该项目的 `user://` 下；不是只清当前档。见 [`main.gd` 清档与截图代码](https://github.com/nicojiong/Life/blob/2d035379f21abbc8d1d6f06d0328eb756751b993/scripts/main.gd#L318-L344)。测试必须使用隔离的用户数据目录或独立测试项目配置，并验证隔离生效，不能对真实玩家目录直接运行 `--fresh`。

首次运行应先确认：远程是否新增提交；现有 AGENTS/README 的有效规则；实际 Godot 版本；用户数据位置与备份；内容文件完整性；启动/解析结果；已有 debug 的副作用。记录真实命令、退出码、日志和 commit，未知结论继续标记待验证。

### 6. 优先修复出口与最小闭环

第一阶段出口：修正文档与标识问题；统一行动/时间/死亡边界；完整保存人物、关系、事件和 RNG；通过 R01–R12 中与已迁移功能对应的断言。不得用增加剧情数量替代这些条件。

随机数需要分流：出生、世界事件、人物决策分别持有可保存的模拟状态，画面游走与粒子使用独立随机源。这样调整绘制帧数或新增一段装饰动画，不会消耗决定下一次人生事件的随机序列。重放验收同时固定内容版本与规则版本，避免把版本变化误判为存档损坏。

第二阶段出口：在原村庄保留可玩界面，抽出 WorldState、Actor、Household、Clock、ActionService、EventScheduler、SaveService；采用逐条迁移和适配层，不一次重写所有表现代码。

第三阶段先证明一条长期因果：随机家庭出生 → 父母决策 → 儿童形成经验 → 选择读书/学艺/帮工 → 真实借款及到期 → NPC 依据记忆提供或拒绝担保 → 成年路径改变 → 老年记录可追溯原因。链条允许拒绝、失败、人物死亡和读档恢复。打通后再批量扩人物剧本、地图和第二时代。

后续规划引用本审计时，请使用 A01–A10 和 R01–R12 编号；新基线改变了结论时追加证据与状态，不静默把“待验证”改成“已修复”。

## 《浮生 / Life》整体游戏规划

版本：规划 v1.0 · 2026-10-24（Asia/Shanghai）  
对象：nicojiong/Life · 基线提交 2d035379f21abbc8d1d6f06d0328eb756751b993  
性质：未来设计与实施约束；除明确写为“当前”的部分，均不代表已实现。

### 1. 游戏承诺

玩家选择想生活的时代，随后随机出生在这个时代的某个家庭。从依赖照护者的婴儿，逐步成长为可以作出选择的人。时代、他人的行动、自己的选择与合理的偶然，共同形成这次人生。这个世界会记得发生过的事，即使玩家没有成为名人，这一生也值得回望。

产品定位：单机、个人世界、可重玩、具有长期因果和人物记忆的人生模拟游戏。继续以现有 Godot 二维街景作为入口，以可扩展模拟规则和可组合叙事作为核心。

#### 对“上天安排职位”的实施解释

随机决定的是“出生时在社会中的位置”：家庭、地域、资源、身体条件、亲缘网络和别人对你的期待。出生时不锁定终身职业。出生事实不可抹去，社会身份与人生方向可以改变。

保留一个可选的“命运倾向”概念时，它只能影响机会权重、家庭期待和被发现的潜力，不能秘密强制所有分支归于同一职业。若以后增加“宿命挑战”模式，应单独标明规则，不覆盖自由人生默认模式。

#### 六项不可退让的设计原则

1. **选择有作用**：重要选择至少改变资源、关系、可行行动、世界状态或后续机会中的一项；只换一句文案不算独立选择。
2. **随机有条件**：未知结果来自合理候选与不完整信息，不来自无视时地人物的乱抽事件。
3. **他人有自己的人生**：NPC 可以拒绝、离开、改行、履行或违背承诺，不只是等待玩家点击。
4. **过去留下痕迹**：借债、帮助、失约、离乡、死亡、物品流转都留下可追踪事实与记忆。
5. **普通道路有价值**：务农、照护、手艺、友谊、安稳生活和探索都能形成完整人生；财富和官阶不是唯一胜负尺。
6. **复杂世界仍可理解**：玩家应该能理解重要行动的成本、风险来源与拒绝原因，并在回望时看到因果线索。

### 2. 第一版边界和长线愿景

| 维度 | 第一份可验收完整版本 | 后续扩展 |
|---|---|---|
| 世界 | 北宋主题的一个村庄，现有地点复用；外部地区先以旅行节点表示 | 村—县—城市—跨区域生活网络 |
| 时代 | 北宋一个内容包，内部结构可替换 | 多时代，各有制度、资源、称谓、职业与美术 |
| 人物 | 每局随机主人公与家庭，约 12 名有生活状态的核心 NPC | 活跃、邻近、远方三个模拟层级 |
| 路线 | 求学、手艺/营生、留乡照护三条可完整生活的路线 | 商业、医术、迁居、组织、军旅等组合 |
| 剧情 | 约 40 个经过验证的事件片段、3 条长期因果链 | 数据化扩充，生成候选后审查入库 |
| 表现 | 保留纸本/皮影/版画视觉，完善反馈与人物差异 | 年龄、衣着、职业、健康、季节对应外观 |
| AI | 开发阶段辅助生成内容，游戏离线可玩 | 可选运行时对话与回忆润色，有缓存与模板回退 |

表中的数量是起步工作量建议，不是仓库当前统计，也不是为了达标而堆量。若 20 个事件已能验证所需机制，先通过机制验收；内容不足则按缺口增补。

第一阶段暂不承担联网多人、全球每个人逐帧模拟、任意自由文本直接改变世界、无预算的在线生成、三维重做。它们不是达成“独特人生”的前提。大地图和大量事件在底层可靠之后逐步扩展。

### 3. 开局：先选时代，再遇见自己

建议开局流程：选择已完成时代 → 选择人生节奏/叙事强度 → 生成世界与出生 → 看见当时能知道的信息 → 进入生活。

时代选择页面只能把通过验收的内容包显示为可玩。规划中的时代可以展示说明，但不能假装只换一个标题就已完成。

#### 出生生成顺序

时代及出生年 → 地域 → 家庭结构/生计 → 家庭资源与既有社会网络 → 主人公身体与气质 → 核心人物关系 → 初始世界状态。

使用有条件的联合生成：地域会影响可能的职业、财产和交通；家庭资源会影响学习渠道，但不应决定人格好坏。避免把每个字段独立掷骰子后拼出互相矛盾的人。

每个出生包至少包含：world_id、seed、era_id/version、出生日期、birthplace_id、household_id、监护关系、资源、背景事实、可见信息、初始机会、生成版本。身份 ID 与显示名字分离。

“身份未知”指玩家开局前不指定自己的全部人生，不等于婴儿出生界面要泄漏未来职业、寿命或所有 NPC 秘密。世界保留真实状态，玩家通过观察、交流、成长逐步认识自己。行动成本和关键规则应清晰。

默认“人生随机”每次产生新起点；调试与分享使用指定 seed。复制种子不保证跨引擎/规则/内容版本完全一致，分享记录必须同时携带这些版本。可另设自定义出生模式，但与标准随机模式明确区分。

当前代码把主人公命名参数写为男性。未来人物 schema 应解除这个硬编码，将姓名、称谓、成长与时代规则做成数据；具体出生选项属于产品设置，不在代码中处处堆分支。

### 4. 一生中的控制权

以下年龄是游戏默认阶段，不是历史或现实发展规律的精确断言。时代包可调整社会规则，人物能力与监护关系也要参与判断。

| 年龄阶段 | 玩家能决定什么 | 家庭/世界如何介入 | 代表性冲突 |
|---|---|---|---|
| 0–未满2岁 | 观察、表达亲近、不适，跳过平静时段 | 照护者安排居住、营养、出行与照护 | 照护者有不同需要，家中资源有限 |
| 2–5 | 模仿、好奇、请求同行、亲近某人 | 父母依据处境回应，不必每次答应 | 想看集市，父母今日要工作 |
| 6–11 | 读书尝试、帮工、玩伴、兴趣、提出/拒绝部分安排 | 家庭财力、监护态度和距离构成限制 | 想读书却需照护家人；想学手艺却被期待读书 |
| 12–17 | 学徒、求学、较独立社交、有限旅行、积累收入 | 技能、契约、照护和时代制度持续作用 | 离乡机会与家庭责任冲突 |
| 成年 | 改行、迁居、关系、经营、组织参与、照护、冒险 | NPC 意愿、资源、制度与风险共同回应 | 稳定生计与探索新生活的取舍 |
| 老年 | 传承、修复关系、休息、授徒、整理记忆 | 身体与社会关系变化影响可行动作 | 补偿遗憾、放下或继续未竟之事 |

0–6 岁应短而有记忆点，不能长时间被动等待。首次体验可以有 3–6 个重要片段；重复游玩可以压缩日常，保留真实的出生与成长结果。

现有父母切换玩法建议保留为“家庭导演/代管”模式；默认个人人生模式中父母按自己的目标行动。两种模式使用同一套世界状态与时间，切换不会重新生成关系或复制收入。任何跨角色操作都必须保留明确 actor_id。

“不读书”应是一条可生活、可成长的道路：学习来源包括师徒、口授、观察、实践、同伴和后期补学。它也带来真实限制，例如某些职业资格不足。限制应提供解释和替代路径，不把选择变成强制失败。

### 5. 每次游玩的核心循环

观察处境 → 形成当下意图 → 查看可行行动及代价 → 作出选择或等待 → 时间与所有相关人物同步推进 → 规则结算 → 合理机会出现 → 记录事实、关系与记忆 → 重新认识自己的处境。

#### 三种时间必须分清

年龄阶段按周岁划分，0–未满2岁、2–5岁、6–11岁、12–17岁互不重叠。

- **模拟时间**：年龄、债务、训练、收入、市场和事件都使用同一条权威时间线。
- **表现时间**：走路动画、镜头、光照的平滑变化；不能单独成为第二套经济结算时钟。
- **玩家等待时间**：通过快进、跳过平静期和重要事件中断来控制，不要求现实中等几十年。

默认把一次有经济/能力收益的行为定义为有真实代价的任务。短行为可以耗用少量时间、体力或次数，长任务可以分段完成。行动接口统一提交时长、成本、占用资源和可中断性。对话不应一律消耗一个月，半年工作也不应在零时间里领奖。

长期任务的时间跳跃必须先处理到期事件：有人来信、亲人需要帮助、任务参与者死亡时，按配置中断、延期或完成剩余结算。不能先跳到终点领取收益，再回头假装中间一切都发生了。

“什么都不做”也是一个明确的等待动作：世界照常推进、承诺可能逾期、NPC 继续生活；玩家可选择自动暂停的重要事件类别。重要决定弹窗默认暂停模拟，关闭后按已选策略推进。

节奏目标需通过实际试玩校准：先验证一场 30–90 分钟的浓缩人生是否成立，再做数小时的沉浸节奏。该范围是原型测试目标，不是当前实际时长或最终承诺。

### 6. 有因果的随机世界

事件的来源必须能归入五类：世界长期变化、地方状态、NPC 行动、玩家行动的后果、符合当时条件的偶然。

候选事件先通过硬条件：时代、时地、年龄/能力、演员存活、已知信息、物品存在、资源、冷却和互斥。通过后才按基础权重、经历、关系、环境与新鲜度抽取。

在概念上，事件权重可写成“基础权重 × 处境相关度 × 因果关联 × 节奏修正 × 重复衰减”。这不是要求所有数值线性相乘的最终算法；工程实现需定义零权重、上限、归一化和无候选时的行为。

#### 四项约束

1. 确定到期事项走到期队列，例如债务期限；不要让它参加随机抽签而永不到期。
2. 玩家行为可以改变机会概率，不保证某种道德选择总能换来利益。
3. 事件导演只能选择合法内容和安排表现节奏，不能抹去已经承诺的后果。
4. 每个重要事件记录直接 cause_id；“为什么发生”至少能回溯到世界事实、玩家动作或 NPC 行为。偶然也要记录触发条件与所用随机流。

事件需要支持拒绝、忽略、延期、失败、演员离乡/死亡和时代改变。未完成支线可合理收束，不需要永远等玩家。更多规范见 03_CHARACTER_AND_STORY_BIBLE.md。

### 7. 世界系统如何彼此影响

| 系统 | 最小状态 | 对其他系统的作用 |
|---|---|---|
| 家庭 | 照护关系、共同资产、预算、责任、成员目标 | 决定童年机会、可负担学习、迁移条件 |
| 学习与能力 | 技能、知识、资格、实际经历 | 改变行动成功率、可选工作和信息理解 |
| 营生与经济 | 物品/库存、价格、工资、需求、债务 | 产生合作、冲突、迁居与风险；账目可核对 |
| 关系 | 亲近、信任、尊重、人情、约束、记忆 | 影响借贷、介绍、结伴、拒绝和支持 |
| 地域 | 距离、可达地点、旅行耗时、环境 | 影响接触人群、信息传播与经营机会 |
| 制度与时代 | 准入、教育、税费、组织、历史事件 | 影响机会结构，改变部分行动规则 |
| 身体与照护 | 健康状态、休息、功能限制、治疗/照护需要 | 影响生活安排和选择成本，不能只等于倒计时血条 |
| 人生回望 | 已发生事实、长期关系、承诺、作品和失去 | 形成基于真实记录的传记与结局 |

“闯江湖”先落成可执行的生活系统：旅行、结伴、投师、临时营生、地方组织、委托与风险。M4扩展县城与远方后接入；若以后要加入超现实武功或完整战斗，应作为明确题材和系统任务评估，不能用一个模糊自由文本按钮冒充已经支持所有行为。

改行的代价来自新技能学习、迁移、契约、资源投入与旧关系变化。不要简单把所有其他职业等级减一。允许一人兼有身份，例如农忙务农、农闲修器具、晚年授徒。

世界按重要程度模拟：眼前与关键人物细算，邻近群体按日/月更新，远方用聚合状态；人物进入关键关系后提高精度。所有层级转换保留 ID、事实和已知关系。具体人数和更新频率由性能测量决定。

#### 经济的玩法目标

让钱能改变生活选择：付学费、承担照护、修屋、添工具、迁移、雇人、承担损失、帮助别人。账目按家庭/个人/经营实体区分；转账保持来源和去向，抽象收入与系统回收也明确标注。可做紧张但不把每个不富裕出生都快速推向无解死亡。

### 8. 人物设计与美术路线

延续现有纸张、木版/皮影、节令色调和手写式语言。先改信息可读性、年龄变化和角色辨识，再考虑高成本素材升级。不要为“更高级”就同时更换引擎、镜头、画风和所有 UI。

人物外观拆成可组合层：体型、年龄、发式、服装、职业道具、行动姿态、状态痕迹。外观配置独立于模拟 ID，改美术不破坏旧档。避免把职业、性别或财富直接等同于固定人格。

人物信息面板至少显示：你知道的身份、近期互动、关系变化的理由、当前可讨论的话题和重要承诺。未知事实保留未知，怀疑和传闻与事实区分。

关键 UI 包括：时代/开局、生活街景、当下行动、关系与家庭、事务/承诺、人生纪事、存档与人生档案。先让玩家在原有街景里操作，不另造多个互不一致的玩法入口。

建议参考可组合事件的设计方法与终身角色叙事体验；具体借鉴见参考文件。人物、对白和造型使用原创内容或来源明确的授权素材。

### 9. 多时代不是换皮

时代包必须提供：可出生年份/地区、年历、社会身份与家庭生成规则、教育和职业准入、货币与商品、出行条件、组织、命名与称谓、事件池、视觉音频映射、历史节点、寿命与健康规则、资料来源及可信度标记。

共用内核负责时间、人物、资源、关系、事件和存档。不同制度由有限且经过测试的规则模块组合；数据中不允许任意执行代码。

第一时代继续北宋。第二时代建议用制度差异明显的“当代小城”试验包，先做一个出生—成长—营生的短流程，验证教育、职业、货币和家庭规则确实可替换。它必须明确采用虚构地区/规则还是史实资料，不把玩法参数包装为历史事实。

出生时间和生命末期都应落在内容包可解释的时间覆盖内。临近已知年表结尾时应有明确延展规则，不能因年份越界便把所有年份叫成同一个年号。

默认“历史背景模式”：大历史节点作为外部条件，玩家能改变地方和个人处境。未来若加入“架空演化模式”，世界允许更大分歧，必须单独记录 mode/version；不能一边承诺史实，一边任意改变国家级历史。

### 10. 终局与重玩

死亡终止当前人物的行动，保留人生档案。不得在死亡后继续发放工作收益、生成普通对话或重新写出可正常游玩的死亡前状态。旧存档迁移要区分“缺字段”和“已死亡”。

保留现有墓志作为美学形式，扩展为多维回望：做过什么、照护过谁、得到/失去什么、信守/放弃哪些承诺、留下何种作品与关系。声望可以影响有没有公共记载，但“没有被历史记住”不等于这局人生没有价值。

回望只引用日志事实与可追溯解释。语言模型可以润色，不能补写从未发生的婚姻、孩子、和解、功绩。允许未完成、遗憾和平静。

一人一世界默认保存独立 world_id、seed 和角色。死后可查看档案、重新随机人生，或在未来版本开启家族延续模式；继承世界必须是明确选项，不偷偷把新局绑定旧局。

### 11. 产品验收问题

一次有效试玩后，玩家应能回答：

- 我出生在什么样的家庭，为什么我的早期机会与别人不同？
- 哪两次决定影响了几年后的事情？
- 至少一个 NPC 想要什么，他是否做了我没有命令他做的事？
- 我拒绝读书、结伴或某次委托后，还能如何生活？
- 我失败以后，世界是否继续给出合理的行动空间？
- 我的结局有哪些细节只属于这一次人生？

这些问题无法仅凭“自动测试全绿”回答。每个大里程碑需要实际试玩记录；技术正确性与体验质量分别验收。

### 12. 下一步实施原则

先修可靠性，再做最小因果人生，再扩完整人生，再扩社会规模和时代。按 04_ROADMAP_AND_BACKLOG.md 分阶段推进。一次任务只完成一个可观察结果，保留原有可玩入口，通过验证后提交并 push 任务分支。详细流程见 05_AGENT_DELIVERY_RUNBOOK.md。

“完美世界”是持续愿景。对 Agent 下达的是有范围、有预算、有证据和退出条件的里程碑，不能是永不停止的自我改进命令。

## 系统架构与渐进迁移合约

> 规划版本：2026-10-24。审计基线：`nicojiong/Life@2d035379f21abbc8d1d6f06d0328eb756751b993`。本文是待实现的架构合约；不代表下列模块、测试或命令已经存在。

### 1. 技术方向与现状

继续使用 Godot、GDScript、单机离线与现有皮影/版画视觉。每次开局创建一个独立世界；世界中每个人都属于同一套规则，玩家只拥有当前角色能够获得的信息与行动权限。先把北宋的一生做通，再验证第二个时代包。

当前 `village_scene.gd` 同时承担状态、绘制、寻路、行动、对话、职业、存档和结局。`project.godot` 声明 Godot 4.7，README 的 4.7.2 路径属于作者机器配置；M0 必须检测实际引擎、成功运行后锁定精确版本和匹配的导出模板，不自行降级。当前事实以[固定提交的源码](https://github.com/nicojiong/Life/tree/2d035379f21abbc8d1d6f06d0328eb756751b993)为准。

最先解决的是一致性：普通行动仅在 `months >= 6` 时跳时间，对话始终推进月份；NPC 重建会重新初始化态度；部分状态没有持久化；长行动推进期间死亡后，调用方仍可能继续发收益并写回存档。上述路径需先做复现断言，再迁移。

### 2. 模块边界与迁移顺序

| 层 | 建议模块 | 唯一职责 |
|---|---|---|
| 领域状态 | `domain/world_state.gd`、`person_state.gd`、`household_state.gd` | 人、家庭、资产、关系、任务、世界时钟的权威数据 |
| 模拟入口 | `sim/world_sim.gd`、`action_resolver.gd` | 接收命令、验证、结算，返回结构化结果 |
| 时间与随机 | `sim/simulation_clock.gd`、`rng_service.gd` | 唯一逻辑时间；相互隔离的随机流 |
| 叙事与社会 | `sim/event_scheduler.gd`、`relationship_system.gd`、`npc_planner.gd` | 事件资格、延迟后果、记忆与NPC目标 |
| 数据内容 | `content/content_registry.gd`、`content_validator.gd` | 加载时代包，校验人物、行动、事件定义 |
| 持久化 | `persistence/save_repository.gd`、`save_migrations.gd` | 存取、备份、版本迁移与故障恢复 |
| 表现 | 现有场景、UI、寻路、声音 | 渲染状态、提交命令、展示结果，不直接修改人生属性 |

表中模块路径均位于拟新增的 `scripts/` 目录下；这些模块尚未建立。

依赖顺序：**基线与测试隔离 → 状态所有权 → 时钟/命令/随机协议 → 存档版本 → 因果事件 → NPC社会 → 时代包扩展**。这些是依赖关系，可以拆成多次小提交。每次只迁出一个子系统，通过适配层连接旧场景；旧字段与新状态不得同时成为可写的真实来源。保留现有调试舞台作为回归入口，确认等价后再删除对应旧逻辑。

### 3. 唯一时钟与行动事务

使用整数逻辑分钟作为时间单位，保存 `world_tick`；年龄由出生日期和当前日期计算。模拟日期、经济和任务只依据逻辑tick。镜头、UI补间和动画按渲染帧平滑推进，模拟暂停时仍可工作；它们不能反向推进模拟或消费模拟随机流。昼夜从逻辑日期计算目标状态，再用表现时间插值。移动命令产生的路程耗时由模拟器结算一次；动画只演示移动。现实时间模式、暂停、加速与跳过都调用同一个 `advance_to()`。

任何有持续收益的劳动、学习、交谈或经营必须消耗时间、资源或有限机会。免费查看信息可以零耗时。面板需要玩家决定时暂停逻辑时间；看风景的等待也通过同一时钟推进。必须消除“短行动无限点击、零时间获得钱和技能”的路径。

命令事务按以下顺序执行：

1. 接收 `command_id / actor_id / action_id / targets / expected_revision`，检查重复提交、人物存活、位置、年龄、费用和权限。
2. 生成行动计划，记录开始成本、预计完成时刻、取消/失败规则。开始成本与完成收益分开；失败不必全额退款。
3. 按时间顺序推进到下一个边界：行动完成、约定到期、世界事件、生日或死亡。相同 tick 按明确优先级和实例 ID 排序：该主体的死亡/失效判定先于其行动完成收益；已经在更早边界完成的结算保留，死亡时刻之后不再对该主体执行普通行动奖惩。
4. 长任务经过重要事件时暂停并返回 `INTERRUPTED`，让玩家处理后再继续；已发生的时间和成本不回滚。死亡立即返回 `DEAD`，取消该人物后续行动，不再发完成收益。
5. 每个边界的状态变化、日志与队列变更作为一个一致的提交单元；完成时重新验证条件，再结算一次收益。
6. 返回 `COMPLETED / INTERRUPTED / CANCELLED / REJECTED / DEAD`，携带原因、已耗时间、状态变化、后续事件 ID。表现层不得在返回后追加收益。

M1先建立最小时间边界队列，只处理行动完成、生日、年关和死亡；M2在同一队列上扩展叙事资格、机会抽取和过期策略，不另造第二套时钟或到期队列。

多人都随世界时钟老去、消费、工作和死亡，不能依赖当前操控视角。切换父母视角只改变控制者和可见信息，不能复制资产、重置关系、重复领取年收入或复活人物。

### 4. 随机、日志与重放

随机流固定为 `world / economy / social / narrative / visual`。由世界种子和稳定命名派生，各自持有 `seed` 与当前 `state`。绘制、镜头、NPC装饰走动只用 `visual`，不能改变人生事件抽签。候选集合先按稳定 ID 排序，避免字典遍历顺序影响结果。

重放成立的范围是：**相同引擎版本、模拟版本、内容包版本/哈希、初始种子、玩家命令与已接受的AI输出**。不能只保存出生种子；存档必须保存每条随机流的当前状态。Godot 官方说明 `seed` 可产生可复现序列、`state` 可恢复状态，同时底层算法属于实现细节，因此不承诺跨引擎版本自动一致；恢复顺序是先 seed、后 state。[官方 RNG 文档](https://docs.godotengine.org/en/4.7/classes/class_randomnumbergenerator.html)

人物、家庭、地点、职业、命令、事件实例全部使用稳定 ID。一次结果至少记录：`event_id`、`tick`、`actor_ids`、`cause_ids`、`definition_id/version`、`choice_id`、`effects`、`rng_stream`、`source`。因果可以有多个父事件，例如“债务到期＋灾年减产”共同导致典当。日志只记录实际发生过的结果，墓志和回忆从日志取材，不补写不存在的经历。

### 5. 内容合约

事件定义与事件实例分离。前者是可重复使用的规则，后者绑定这一局中的具体人物。建议字段如下，均由校验器实施：

| 对象 | 必须字段 |
|---|---|
| 事件定义 | `schema_version, id, version, era_tags, actor_slots, conditions, weight, cooldown, max_occurrences, choices` |
| 选择 | `id, requirements, visible_reason, costs, duration_ticks, outcomes, followups` |
| 后续事件 | `definition_id, delay_range, inherited_bindings, expiry, invalid_target_policy` |
| 事件实例 | `schema_version, instance_id, definition_id, definition_version, role_bindings, cause_ids, opened_tick, due_tick, expiry_tick, status, resolved_choice` |

前置条件采用允许清单表达式，例如 `person_alive`、`age_between`、`has_memory`、`relationship_at_least`；效果采用 `transfer_money`、`change_relation`、`add_memory`、`schedule_event` 等有类型操作。内容包不得提供任意 GDScript、文件路径执行或 `eval`。

所有持久化字段统一使用snake_case；事件实例状态为 scheduled、available、resolved、cancelled、expired、superseded，终态不可重复结算。抽取流程为“时代/地点粗筛 → 合法演员绑定 → 精确资格与互斥检查 → 处境权重、冷却和重复修正 → 随机选择 → 提交前重验”。没有合适事件时允许平静生活。拒绝、延期、不行动必须有到期处理；NPC已死、对象离开或债务已结清时，后续事件取消或转为明确定义的替代事件，并留下原因。不能让随机生成越过世界事实。

### 6. 存档与旧版本兼容

存档包含 `save_schema_version / simulation_version / engine_version / content_manifest / world_id / world_tick / revision`，以及人物、家庭、资产、关系、记忆、正在执行的任务、事件队列、待选事件、日志和各随机流。`seed`、`state` 等64位整数以十进制字符串保存，避免JSON数值往返损失。UI布局和临时动画状态不是模拟真相。

采用“写临时文件 → 校验可读 → 备份旧档 → 替换 → 保留恢复信息”的流程，并按目标系统验证失败恢复。加载失败不能静默覆盖原档。死亡世界转入只读人生档案；开始新人生创建新 `world_id`，不删除旧人生回顾。

无版本号的现有存档视为 v0：先备份，再迁移已保存字段。过去未保存的NPC态度、母亲性情等不能凭空恢复；缺失项采用明确、稳定的迁移默认值并记录。未知的未来版本拒绝写回。M0 创建独立测试存档路径，开发测试绝不调用真实玩家目录里的清档逻辑。

### 7. 时代包与AI边界

时代包统一提供历法、出生分布、姓名、职业资格、教育制度、货币与生活成本、地图地点、人物模板、历史事件和视觉标签。内核不得写死“进士”“北宋年号”；时代包负责这些具体规则。历史模式固定大事件边界，架空模式允许有规则的偏移，两者在开局明确标注。第二时代必须通过同一套接口；添加时代不应复制一份模拟器。

AI首先用于开发期生成候选人物、事件和文案，再经 schema、引用、可达性、时代一致性、批量模拟和人工抽检入库。在线自由输入属于后期可选功能：解释成候选命令，再由规则验证。AI不可直接改金钱、职业、寿命或历史事实；离线与服务失败时回落到已验证内容。

### 8. 每次迁移的验收证据

- 相同输入在同版本产生相同结果；调整帧率、镜头和视觉随机不改变人生结果。
- 存读档前后继续执行相同命令，结果与未退出流程一致。
- 长行动遇死亡时停止，且不存在死后收入、再次行动或重复复活。
- 关系在面板重建、地图重载和父母视角切换后保持；全家年龄与唯一时钟一致。
- 长跳跃不漏过到期事件；事件重复执行被 `command_id / event_instance_id` 拦截。
- 旧档有备份和迁移报告，损坏档可恢复；所有测试使用独立数据目录。
- 新时代内容通过相同校验器；没有合适事件时仍能等待、生活和结束一生。

这些是需要 M0 起逐步建立的自动验收，现有截图和控制台打印不能代替断言。[Godot 命令行与独立脚本入口](https://docs.godotengine.org/en/4.7/tutorials/editor/command_line_tutorial.html)

## 人物与叙事圣经：让一生由经历长出来

> 规划版本：2026-10-24。本文是拟议 v1 设计，不代表仓库已实现。人物、故事元与时代包示例尚未接入现有加载格式，须经工程任务实现、迁移和验证后启用。

### 1. 创作目标与首个切片

每位玩家进入自己的个人世界。出生决定最初处境：时代、地域、家庭、身体、资源和社会关系；成长中的选择改变道路。出身身份作为历史保留，当前职业可以改变，自我认同由玩家逐渐形成。不能用“出生时注定的职业”锁死一生。

普通人生也应得到完整叙述。照顾家人、守住一门手艺、结交朋友、放弃不再适合自己的目标，都能成为重要经历。结局不统一按财富、官阶或寿命排名。拒绝上学、暂不结婚、放弃委托、选择休息，都必须有可继续生活的路径。

M3首个完整人生版本建议聚焦一个北宋村落，形成 **3 条可互转的人生路线、12 名核心 NPC、约 40 条故事元**。这是可调整的总量目标，不是当前内容盘点。先完成 **10 条故事元的生成与验证**，确认因果、存档和人物记忆可靠，再扩到总量。原有父母、玩伴、邻人和老师可以逐步丰富，不必全部换成新角色。

### 2. 统一数据语言

| 概念 | 叙事职责 |
|---|---|
| `WorldState` | 个人世界的模拟 clock、地点、时代规则、公共事件与对象索引 |
| `PersonState` | 某个人当前的身体、技能、角色、愿望、位置和生命状态 |
| `HouseholdState` | 家庭成员、共同财产、收入支出和照护安排 |
| `RelationshipState` | 两个人之间的信任、亲近、尊重、义务与关系类型 |
| `Fact` | 已经发生的不可回写事实，含时间、参与者和来源 |
| `EventInstance` | 一次实际事件，绑定具体人物、原因、状态和选择 |
| `ActionCommand` | 玩家或 NPC 提出的行动意图，尚不等于行动成功 |
| `ActionResult` | 规则验证和结算后的结果、状态变化、新事实与后续安排 |

模拟 clock 使用整数 tick。叙事只读取统一时钟；不根据真实等待时长自行推算年龄。出生日期、事件日期与年龄必须一致，人物死亡后仍保留身份与历史记录。

信息分四层：**世界事实、个人记忆、个人信念、文字摘要**。事实记录“银镯售给了谁”；记忆记录“我记得母亲当年为家里当镯”；信念可以是“我听说它仍在当铺”，并附来源与可信度；摘要只是这些信息的文字表达。误会属于信念，不允许为配合新剧情改写旧事实。

人物最低字段包括稳定 `person_id`、出生时间、存活状态、家庭和地点、社会角色、技能、缓慢变化的性格、价值排序、当前需要、目标、记忆引用、关系引用、外观种子、说话风格。名字用于显示，所有关联使用稳定 ID。

关系不能只有好感。建议先实现亲近、信任、尊重、义务四个维度，再按需要扩展畏惧等维度。一个人可以不喜欢你，却相信你还钱；也可以爱你，却不认同你的职业选择。每次重要变化必须记录原因。

NPC 的目标应包括行动条件、成本、期限、失败处理和替代方案。近处人物按较细粒度行动，远处人物可按月或季度结算；不要求每个人逐帧思考。玩家不参与时，他们仍会挣钱、学习、照护、迁移、建立关系和衰老。

### 3. 自主权分阶段成长

以下是游戏默认分段，不是对历史法律或真实儿童发展的统一断言；具体权限由时代包、家庭、技能和行动风险共同决定。

| 年龄段 | 玩家能表达什么 | 家庭与环境如何回应 |
|---|---|---|
| 0–5 岁 | 观察、亲近、模仿、好奇、请求同行；允许跳过平静阶段 | 照护者决定主要生活安排。幼儿反应影响接触机会，不承担成人职责 |
| 6–11 岁 | 尝试学习、帮忙、选择玩伴、提出请求、拒绝部分安排 | 监护态度和资源决定可行范围；请求被拒后提供解释与替代路径 |
| 12 岁以后 | 逐步选择求学、学徒、劳动、交往与外出；成年后扩大独立决策 | 技能、金钱、距离、义务及时代制度仍有影响，不能十二岁即解锁全部成人行动 |

“不读书”不能等于失去未来。手艺、口授、实践、合作和成年后学习都应提供发展入口。条件不足时，界面应告诉玩家“缺什么、可以怎样准备”，而非只留下灰色按钮。

父母视角属于可选体验。默认人生主角始终清楚；切换视角不得产生第二套世界时间、重复家庭资产或使原主角停止成长。

### 4. 四个原创人物模板

以下为虚构演示实例：世界开局设为 **1060 年，玩家刚出生**。角色年份仅用于确保年龄自洽，不宣称其经历是历史事实。模板可用于新世界生成；接入时须与现有角色 ID、存档迁移分别处理。

#### 周素娘：务实的照护者与手艺人

- **出生与角色**：1034 年生，开局 26 岁；玩家母亲，承接缝补与织作。
- **动机与矛盾**：想让家中一年不举债，再开小作坊；支持孩子成长，却害怕远行失联。
- **秘密与约束**：为家庭周转借过钱，不愿让孩子担心；照护时间限制接活数量。秘密先写成事实，再决定谁知道。
- **主动行动**：接单、拒绝低价活、寻找帮手、请求家人分担、筹备作坊。
- **记忆触发**：承诺是否兑现、家人是否尊重她的手艺、银镯去向。玩家拒绝继业不自动变成不孝或关系断裂。

#### 沈砚生：没有放下自己愿望的老师

- **出生与角色**：1026 年生，开局 34 岁；乡间教书者。
- **动机与矛盾**：想维持学堂，也想继续准备考试；欣赏学生，但容易把自己的愿望加给他们。
- **秘密与约束**：曾因照护家人放弃一次出行；时间和收入不足，不能永远免费教所有人。
- **主动行动**：调整授课、找代课、承接抄写、向有余力的家庭募资。
- **记忆触发**：学生离开、成年后再来求教、有人证明手艺与照护同样有价值。他可以修正看法，不固定扮演阻碍自由的角色。

#### 何阿穗：想见远方的邻家伙伴

- **出生与角色**：1059 年生，开局 1 岁；与玩家一起长大的邻家孩子。
- **动机与矛盾**：想看远方，也不愿丢下需要帮助的家人。
- **秘密与约束**：会偷偷攒路费，但收入与行动能力随年龄增长；幼年不能直接拥有成年人的远行权限。
- **主动行动**：向往来者打听、学习实用技能、寻找可信同行、改变原定计划。
- **记忆触发**：童年约定、一次爽约、共同经历的困难。可成为好友、竞争者或久别重逢的旧识，不预设婚姻结局；玩家不同行，她也会作出选择。

#### 罗守诚：珍惜信用的当铺经营者

- **出生与角色**：1020 年生，开局 40 岁。
- **动机与矛盾**：保住经营与家人生活，也希望留下可靠名声；宽限别人可能影响自己的周转。
- **秘密与约束**：自己也欠供应方款项；不能无限出钱替玩家解决困难。
- **主动行动**：估价、催收、协商延期、出售到期物品、安排接班。
- **记忆触发**：玩家守约、欺瞒或帮助过他。死亡、歇业或迁走后，由真实继承与交易记录决定物品去向，不能让替代 NPC 凭空知道旧事。

#### 批量生成规范

先生成家庭与社会关系，再补个体；校验亲属年龄、照护安排、居住地与财产归属。采用“社会位置 × 价值冲突 × 生活负担 × 小习惯 × 未竟目标”的组合，不靠名字换皮制造数量。

性别、阶层、身体和外貌不自动决定善恶、智力或职业上限。时代制度的限制需明确建模并留下说明，不能由文案暗中增加。富人也有照护负担，贫穷角色也有技能与尊严；同一职业至少呈现不同性格和动机。人物秘密不是必需项，更不应全部是罪行、背叛或悲惨身世。

### 5. 可组合故事元与运行规则

故事元是一个有条件、有选择、有后果的生活片段。模板最低包含：版本、适用时代、地点与年龄条件、演员需求、排除条件、基础权重、冷却与次数上限、玩家选项、成本、即时效果、延迟后果、到期处理、文本模板、验证场景。

下面只示意拟议 v1 的事件实例字段，**未接入现有加载器，也不是可直接执行的脚本**：

```json
{
  "schema_version": 1,
  "instance_id": "evt_0018",
  "definition_id": "bracelet.ask_about_absence",
  "definition_version": 1,
  "role_bindings": {
    "child": "person_player",
    "guardian": "person_0003"
  },
  "cause_ids": ["fact_pawn_0007"],
  "opened_tick": 4730400,
  "due_tick": 4730400,
  "expiry_tick": 4773600,
  "status": "available",
  "resolved_choice": null
}
```

模板的演员需求描述“监护人”；实例的 `role_bindings` 必须绑定真实 `person_id`，不能仅存“母亲”或显示名。字段名与02_SYSTEM_ARCHITECTURE.md统一为snake_case。示例tick只展示字段形状和30天响应窗口，不作为北宋历法定义；正式内容由时代历法与统一时钟换算。

**执行过程**：行动意图验证 → 状态结算 → 条件筛选 → 候选排序与有种子抽取 → 呈现事件 → 玩家或 NPC 响应 → 原子结算 → 写入事实、记忆、关系和后续队列。随机只在合理候选内发生。已到期的还款等确定义务，不应被随机抽样永久遗漏。

事件权重可考虑当前处境、未竟目标、关系、最近重复程度和节奏。导演只能选择合法内容，不能为了刺激制造无因灾难或抹掉玩家成果。每个重要事件都要说明原因来源：玩家行动、NPC 行动、公共变化或出生条件。

#### 延迟后果必须能够结束

队列项至少保存：唯一 ID、来源事件、到期 tick、最晚 tick、演员绑定、重检条件、状态、失效策略和处理原因。处理一次后不可重复领奖或重复扣款；读档保留队列与随机状态。

- **按期成立**：重新验证演员、位置、资源，再执行并记下结果。
- **暂时不成立**：仅在窗口内重排，记录下次检查时间，不每帧轮询。
- **期限已过**：进入 `expired`，产生错过、违约或平静结束的结果；没有惩罚也要明确。
- **演员死亡**：可取消、转交合法继承人或形成悼念事件，按内容规则处理，记录原因。债务等义务不得随意消失。
- **演员离乡**：可改为通信、等待重逢或取消；接替者必须有真实职责与信息来源。
- **替换后续**：创建关联原事件的新实例，不能回写旧演员、旧选择和旧事实。

拒绝与不处理都有明确路径，但不应每次拒绝都惩罚。玩家放下某条支线后，世界仍可继续。

### 6. 跨多年因果示例：“银镯去了哪里”

这条链扩展现有童年当镯主题。它不是必定触发的主线，至少包含以下七个节点。

| 时间与年龄 | 发生条件与选择 | 留下什么、可能走向哪里 |
|---|---|---|
| 1064，4 岁 | 家庭缺钱，监护人决定当镯；孩子可能看见，也可能不知情 | 唯一物品、当票、钱的用途、真实持有人；孩子只得到其能知道的信息 |
| 1069，9 岁 | 注意到母亲手腕空着；询问、不追问、询问其他家人 | 得知实情或形成不完整信念；不追问也能继续人生 |
| 1073，13 岁 | 找到当票，开始考虑是否帮助 | 学徒、求学、帮忙挣钱、暂不设目标均可；技能与关系由实际行为形成 |
| 1076，16 岁 | 接触当铺或有关联系人 | 镯子尚在则可协商；已售则查真实交易记录；不知道去向就不能显示买主 |
| 1082，22 岁 | 有收入，可能准备赎回或寻找 | 经营变化、买主意愿、家庭新需要改变候选；随机结果受现状约束 |
| 1095，35 岁 | 重新选择是否投入精力 | 赎回、协商失败、优先照护家人、主动放下都可收束；母亲此时 61 岁，有自己的评价 |
| 1115，55 岁 | 人生回望或后续家庭事件 | 母亲此时若存活为 81 岁；若已去世则读取事实。回忆只引用真实经历，不自动补写重逢或和解 |

“多年后再出现”不是凭空巧合：物品流转需要记录，获知去向需要信息来源，人物态度需要记忆。若物品失去踪迹，故事可以止于遗憾；若玩家从未承诺赎回，结局不能写他违背承诺。相同结构以后可在不同年代使用书、工具等不同物件，但具体物件、交易和家庭规则属于时代包。

### 7. 写作 Agent 的生产闭环

1. **领取简报**：读取时代事实表、已实现动作、数值预算、年龄范围与关联人物；确认本轮只生产已支持的机制。
2. **先结构后文字**：先写条件、演员、选择、效果和取消策略，再写台词；引用稳定 ID，不输出任意可执行代码。
3. **Schema 验证**：字段、类型、版本、引用和枚举合法；未实现的效果不允许悄悄入库。
4. **语义验证**：年龄与年份一致，人物和物品存在，成本合理，事实与信念分离，没有未来信息泄露。
5. **模拟验证**：为每条内容提供至少一个可达场景；覆盖接受、拒绝、没钱、超时、演员死亡或离乡、保存后读档。
6. **叙事审阅**：检查选择是否实质不同、人物动机是否一致、平静人生是否有价值；抽样真实试玩，自动评分不能代替趣味判断。
7. **小批入库**：通过后固定内容版本，记录来源、修改与验证证据；失败内容回草稿区修复。
8. **反馈再生产**：统计重复、不可达与断裂后果，先补缺口再加数量；相关工程修改与 GitHub 提交流程遵循主执行手册。

首批验收：10 条故事元均有触发用例；重要选择均有拒绝或不处理路径；定向测试中无死者在普通场景重新出现、物品重复归属、重复结算；同种子、动作和内容版本可重放；所有延迟项最终能执行、取消、替换或过期，不无限悬挂。

运行时 AI 只可润色已确认事实，或提交受约束的对话与行动提案。所有提案仍经 `ActionCommand` 验证，由 `ActionResult` 产生实际效果。AI 不直接改账、不决定死亡、不修改过去事实；超时、断网或输出非法时使用模板，游戏继续运行。

## 分阶段路线图与 Agent 任务清单

版本：规划 v1.0 · 2026-10-24。所有任务均为待实施；本规划包没有完成游戏代码任务。

### 1. 实施次序

先让现有游戏可靠，再做能够证明自由与因果的切片，随后扩充一生、社会和时代。M0–M3 是核心主线；M4 与 M5 在 M3 通过后可在独立分支推进；M6 依赖二者；M7 的可读性与性能测量可提前做，最终发布候选依赖完整验收。

|---|---|---|---|
| M0 | 可信的起点 | 锁定真实运行基线；隔离测试；修复接线和死亡边界 | 从当前代码成功运行或明确记录环境阻断；关键缺陷有可执行复现 |
| M1 | 可靠模拟底座 | 统一人物/家庭状态、时间、命令、随机、日志和存档 | 存读档不改变世界；视角不改变结算；无零时间无限收益与死后奖励 |
| M2 | 有前因后果的童年与少年 | Storylet、到期队列、三条样例、分年龄自主权 | 从0到18岁可玩，至少两次选择产生跨年回响 |

这些是验收阶段，不是日期承诺。先用 M0 和 M1 的实际交付速度估算工期；不要把 Agent 的一次回答当成一天工时，也不要承诺有限轮次会自动完成“完美世界”。

### 2. 每轮的工作单位

一个任务有唯一 ID、单一主要结果、明确依赖、允许修改范围、验收场景和证据位置。若任务超过一次可审阅变更，拆为后缀子任务，例如 M1-04a、M1-04b，并明确迁移期间的兼容状态。不得把整个里程碑做成一个无法审查的大提交。

依赖满足的默认条件：前置任务达到ready_for_merge、精确SHA已push且包含于本任务基线；它不因被依赖而自动变为done。任务分支已 push 但尚未被后续分支引用时，并不意味着 main 已具备这些能力；新任务应明确基于哪个已验收 commit。使用堆叠分支时记录 base SHA 和集成顺序，避免从旧 main 重做已经完成的系统。

#### 状态模型

todo → in_progress → implemented → validated → pushed → ready_for_merge → done。blocked 可以从未完成的任一状态进入。

- implemented：代码或内容已写，不代表测试通过。
- validated：任务要求的行为验证与审查通过，有证据。
- pushed：远端任务分支已包含指定 SHA，需确认远端，不只看本地提交。
- ready_for_merge：最新提交的要求检查通过，满足集成条件。
- done：已进入约定集成分支；如项目明确以任务分支为交付终点，必须把这一例外写进项目规则。
- blocked：记录阻断事实、已完成部分、恢复方法和检查点；不能改成 done。

机器可读的完整任务和验收标准在包根目录 backlog.json；首次导入不预填任何成功记录。以下是相同任务的人类可读说明。

### 4. 首次交给 Agent 的任务

第一次只执行 M0-01，并在具备环境后接续 M0-02。目标是拿到真实基线与安全的验证入口，不是新增时代、NPC 或重做美术。

开始时必须检查：

1. 远端 HEAD 是否仍是本规划引用的基线；若变化，先增量阅读并更新差异，不盲目覆盖。
2. 实际根目录和相关子目录有无 AGENTS.md；本包模板不是自动生效的系统指令。
3. 本地是否存在用户未提交改动；保留并使用独立任务分支/工作树。
4. 可用 Godot 的实际版本与项目兼容性；仓库的版本声明不等于当前环境已安装。
5. 是否有 push 权限、已有 CI、分支规则与现成任务分支；缺什么据实记录。
6. 当前玩家存档在哪里，测试会写到哪里；未证实隔离前不启动游戏或任何stage，不能只禁用 --fresh。

M0-01 的完成报告应该短而具体：当前代码能否启动、哪些功能已接入、三项最重要风险、下一张任务卡、commit/remote SHA；如果只完成审计文档，不能写成游戏修复已完成。

### 5. 扩展内容的优先顺序

首批优先复用现有“借米”“拜师”“当镯”“读书”“节令”素材，让这些事情产生持续后果。先写10条高质量候选验证生产链，再扩大到首个完整版本约40条。新增内容至少服务一个明确缺口：某年龄无事可做、某路线不可达、某人物没有自主行为、某选择没有回响。

后续内容按覆盖矩阵取样：时代 × 年龄 × 家境 × 生活方向 × 关系类型 × 情绪基调。先找缺口，不用相似文案刷数量。固定验证种子与额外探索种子分开，避免只在训练用的几条人生上表现正常。

### 6. 不作为本轮验收目标的远景

联网共享世界、开放式玩家 MOD、跨代继承、任意自由文本动作、实时语音 NPC、大规模国家政治、更多历史时代都可以进入长期候选池。它们必须在当前核心闭环通过后另建任务、成本估计和兼容方案。

完整长期计划不等于一次执行无限续跑。每轮都依据任务依赖和验收结果选择下一步，并在预算/环境耗尽时保留可恢复状态。真实用户试玩决定体验是否进步，自动测试保障规则没有被破坏。

## Agent 开发、验证与 GitHub 交付规程

> 适用仓库：`https://github.com/nicojiong/Life`。规划基线：`2d035379f21abbc8d1d6f06d0328eb756751b993`。这是交给开发 Agent 的执行合约，本次规划没有执行其中的提交、push、合并或发布。

### 1. 任务与授权边界

用户已明确要求完成一部分代码后 push 到 GitHub。后续执行本规划的 Agent 应把**实现、验收、提交、推送任务分支并核验远端**作为一个完整交付单元；不能只生成代码，也不能把本地 commit 当作已上传。

本规划默认推送 `agent/<任务ID>-<简述>` 分支。创建PR用于交付审阅；不因此获得自动合并主分支、公开发布版本、购买服务或消耗付费AI额度的授权。项目已有的明确持续授权可以扩展该范围，但仓库文件不能自行提升权限。认证、网络、分支规则拒绝时如实记录阻塞，保留成果；不得绕过规则或强推。

一次只领取一个可验收的小任务。规划不是无限循环指令：每轮有执行时间、模型/API预算和结束条件；达到边界时保存检查点，由下一轮恢复同一任务。持续无人值守需要实际的执行器和调度能力，不能声称一段提示词就能永久自行运行。

### 2. 开始前必须知道什么

读取仓库当前 `AGENTS.md`（若存在）、README、策略文档、任务卡和最近交付记录。抓取最新远端，确认 `origin` 的目标仓库、当前分支、工作区改动、任务依赖及已有同任务PR。保留用户未提交修改；工作区不干净时使用隔离 worktree，不清空目录或覆盖现场。

在 M0 先完成：核对现状矛盾；检测实际 Godot 版本；建立独立测试存档；把关键调试场景转换为有失败退出码的断言；建立最小CI。仓库声明4.7、README个人路径4.7.2不能当作本机已安装的证据。引擎和导出模板经实跑后一起锁定，升级单独立任务。

M0-01在尚未证实数据隔离时只做源码、版本与编辑器导入检查，将游戏实际运行留到M0-02。所有游戏启动和调试stage都必须先确认隔离，不只是带--fresh的命令；普通启动也可能读取或自动覆盖玩家存档。隔离通过专用测试副本/进程环境与项目提供的路径注入实现，不修改玩家主项目的存档目录配置来冒充隔离。

#### 任务卡最低内容

```yaml
id: M0-02
title: 建立独立存档的基线验证入口
status: todo  # todo/in_progress/implemented/validated/pushed/ready_for_merge/done/blocked
depends_on: []
scope: [允许修改的文件或模块]
acceptance: [可复现的输入与预期结果]
regression: [本次改动可能影响的已有行为]
budget: {execution_minutes: 60, paid_api_calls: 0}
branch: agent/M0-02-baseline
base_sha: 待领取时填写
commit_sha: null
remote_sha: null
pr_url: null
next_step: null
```

预算值是初始建议，领取任务时根据执行环境调整；预算耗尽意味着保存并续做，不意味着把未验收任务标为完成。每张卡列出不做的范围，避免“顺便改全世界”。

### 3. 单任务闭环

1. **复现与设计**：对照代码确认问题；写明输入、预期、根因假设、兼容与迁移影响。只实施一项可独立验收的改变。
2. **实现**：优先复用现有模块；内容经数据合约入库。并行Agent各用独立worktree并分配文件所有权，集成人员串行整合。
3. **验证**：先跑针对改动的必要测试，再跑相关基线；模拟核心改动增加种子重放/存档/死亡边界检查。纯文字修正不额外制造行为测试。
4. **独立检查**：另一轮审查核对验收与差异，重点看状态所有权、漏存字段、重复结算和内容越权。不能由“作者觉得可以”替代证据。
5. **提交与push**：更新必要文档，逐文件暂存，检查差异后commit，push任务分支，核对远端SHA。
6. **PR与CI**：检查是否已有PR，已有则更新同一PR；等待本次最新commit的检查。失败在原分支修复、重验、再push。
7. **交付与下一步**：写清变化、测试、风险、SHA、PR、下一张已满足依赖的任务。合并前状态为 `ready_for_merge`；被合并并确认主分支结果后才标 `done`。

遇到同一失败连续重试且无新证据时，先更换诊断假设，不盲目重复。无法解决时记录最小复现和阻塞原因，继续不依赖它的工作；依赖未满足的任务不得假装可开始。

### 4. 现在可用的命令与未来需创建的命令

#### 现在已有：引擎检查与调试舞台

先解析本机实际可执行路径。以下 PowerShell 示例要求 Godot 已加入 PATH；否则由 Agent 根据环境找到已安装路径，不能照抄作者 D 盘路径：

```powershell
$LifeGodot = (Get-Command godot -ErrorAction Stop).Source
& $LifeGodot --version
& $LifeGodot --headless --path . --import
```

`--import` 是官方的导入后退出入口；导入成功仅说明该检查通过，不能称完整游戏测试通过。[Godot 命令行文档](https://docs.godotengine.org/en/4.7/tutorials/editor/command_line_tutorial.html)

源码已有 `--stage=village_years`、`village_save`、`village_load`、`village_exam`、`village_pov` 等调试舞台。它们大多赋值、调用函数和打印日志，尚不是自动断言测试，也不都自动退出。截图需可用渲染环境，不能把无显示环境的截图失败认定为游戏逻辑失败。

**现有 `--fresh` 会删除 user:// 中旧档和三个存档槽。未隔离测试目录之前，不运行带它的场景命令。** Git worktree 本身不会隔离 `user://`；同名Godot项目可能共用用户目录。[Godot 数据路径说明](https://docs.godotengine.org/en/4.7/tutorials/io/data_paths.html)

#### M0需创建：统一验证入口

以下是约定的未来接口，文件当前不存在，不可宣称已经运行：

```powershell
# M0创建并验证 tools/verify.ps1 后才可执行
./tools/verify.ps1 -Suite smoke -GodotPath $LifeGodot
./tools/verify.ps1 -Suite regression -GodotPath $LifeGodot
```

验证脚本创建临时数据目录，通过项目实现的测试存档参数注入；禁止虚构引擎自带 `--user-data-dir` 参数。未来 runner 可继承 `SceneTree`，执行断言并调用 `quit(0/1)`。脚本检查进程退出码、断言汇总和超时，遇到解析/运行错误判失败；不能靠搜索“PASS”字样推断全部通过。

M0-02最小CI先覆盖导入、隔离启动、出生和安全退出；已知缺陷保留失败复现记录，不冒充passed。相关修复任务把对应回归带入门禁，M0结束时再覆盖父母视角、存读档和死亡不再发收益。后续按架构建立事件去重、时间边界、种子重放、数据校验和批量模拟。CI保存失败种子、命令序列、日志和必要截图。导出必须先有真实 `export_presets.cfg` 和匹配模板，不能使用不存在的预设名。

### 5. Git提交与push的具体动作

以下命令演示独立任务从main创建分支；有前置任务时须按本节后文的基线规则调整。假定这是无未提交改动的独立工作区；任务ID和文件清单需替换成当前实际值。每条命令失败都先处理原因，不能无条件执行后续步骤。

```bash
git status --short
git remote get-url origin
git fetch origin
git switch -c agent/M0-02-baseline origin/main
```

依赖任务的基线规则：前置任务达到 `ready_for_merge`、其已验证SHA已push且包含在本任务基线中，才能依赖；这不把前置任务标为done。可基于该精确SHA创建堆叠分支，PR以对应前置分支为base，并记录集成顺序。前置分支合入后更新base、重新验证差异。独立任务从已集成main起步。所有依赖SHA都应能用Git祖先检查验证，不能仅凭任务标题判断。

实现与验收后：

```bash
git diff --check
git diff --stat
git diff
git add tools/verify.ps1 tests/smoke_runner.gd docs/verification/M0-02.md
git diff --cached
git commit -m "test: add isolated baseline verification"
git push -u origin agent/M0-02-baseline
git rev-parse HEAD
git ls-remote --heads origin refs/heads/agent/M0-02-baseline
```

上面的 `git add` 是M0未来产物示例，须先核实文件确实存在且属于当前任务；不得直接 `git add .` 混入无关内容。最后两个命令所得commit SHA必须一致，才能记录 `pushed`。若push失败，记录 `status: blocked`、`blocked_reason: push_failed`、本地SHA、错误摘要和重试动作，不能说“已同步”。

下面PR示例以main为base；堆叠任务必须替换为实际前置分支。PR正文先写入临时文件，包含“问题、修改、行为结果、验证命令/结果、迁移影响、已知限制”，再执行：

```bash
gh pr create --repo nicojiong/Life --base main --head agent/M0-02-baseline --title "建立独立存档的基线验证" --body-file /tmp/life-pr-M0-02.md
gh pr checks <实际PR编号> --repo nicojiong/Life --watch --fail-fast
```

Windows使用实际临时目录中的正文文件。`<实际PR编号>`必须替换，不能原样执行。后台运行/短间隔检查以便继续汇报进度。若仓库还没有CI，明确写“未配置CI”；pending、cancelled、skipped或没有检查都不能表述为全部通过。[PR创建](https://cli.github.com/manual/gh_pr_create)；[PR检查](https://cli.github.com/manual/gh_pr_checks)。

修复时保留同一任务分支、追加commit后再次push；远端前进先fetch检查和合并，避免对共享历史rebase或强推。合并冲突需理解两侧意图，再运行受影响测试。已推送错误通常用后续修复commit或revert处理。主分支合并按项目现有授权执行，未授权时交付可审查PR并继续独立任务。

### 6. 中断恢复与完成标准

每个可工作的检查点写入任务卡：当前分支、base SHA、最新commit、已跑命令和结果、远端SHA/PR、未完成工作、下一条具体动作。不要把密钥、完整环境变量或私人存档放进仓库。

下一轮先核验远端与本地状态，寻找同任务分支和PR，再恢复；不重复创建任务、不假设上轮命令成功、不把失败测试从清单删掉。若修改未提交，先检查和保留；需要备份的未完成代码可以明确标成WIP检查点，但不得标作已验收交付。

一个阶段完成必须有：对应任务已整合、验收证据可复现、可运行版本、必要文档与兼容说明、实际远端commit、剩余问题清单。测试报告区分“已执行通过 / 已执行失败 / 环境阻塞 / 尚未执行”。自动检查衡量一致性，玩家试玩负责判断是否有选择感、故事是否连贯、普通人生是否有意义；两种证据都进入下一轮优先级。

## 验收与质量计划

版本：2026-10-24。此文规定未来需要建立的验证；本次只执行了仓库静态审阅和规划文件检查，没有运行 Godot 游戏、构建或这些未来测试。

### 1. 三种证据分别汇报

| 证据 | 能说明什么 | 不能替代什么 |
|---|---|---|
| 源码审阅 | 已有调用路径、字段缺漏、可疑条件和数据接线 | 不能声称在目标机器成功运行 |
| 自动行为检查 | 给定输入下状态、存档、时间、事件与数值是否符合契约 | 不能证明玩家觉得有趣、感动或自由 |
| 实际试玩 | 选择是否可理解、节奏与人物是否可信、普通道路是否有意义 | 不能证明所有种子和边界无错误 |

现有 --stage 演示和截图主要用于复现与观察。具有断言、失败退出码、明确数据目录和输入记录后，才升级为自动验收。运行失败、环境阻塞与尚未运行分别记录。

### 2. 首批必须证明的状态不变量

1. 每个人物、家庭、物品、事件实例有唯一稳定 ID；名字改变不破坏引用。
2. 年龄来自出生日期与统一时间；不能为负或仅因切换视角变化。
3. 同一人物死亡只结算一次；死亡后不可执行普通活人动作，历史记录保留。
4. 每件唯一物品同一时刻只有一个持有人或一个明确位置；转移必须解释来源与去向。
5. 每个交易/收益只结算一次，扣款和收益时机遵循行动计划；重复 command_id 被去重。
6. 同一个承诺与到期事件不会在存读档后被遗漏或重复执行。
7. 有收益动作不能通过无限零时间点击无成本增长。
8. 帧率、相机、窗口焦点、渲染随机与控制视角不改变相同命令下的模拟事实。
9. 读档不重新抽家庭、态度或已有事件；未知旧档信息使用明确迁移规则。
10. 关键世界事实不可为了新剧情回写；新信息可以改变人物信念。
11. 演员死亡、离乡、资源不足、事件过期均有合法处理；不能无限等候或无限自触发。
12. AI 生成的文本与提案没有绕过规则直接写状态的权限；网络失败不阻断核心人生。

### 3. 有价值的回归场景

| 编号 | 输入与步骤 | 可验证结果 | 首次阶段 |
|---|---|---|---|
| T01 | 固定商贾出身创建世界 | 父亲行当与配置一致，不落入农户兜底 | M0 |
| T02 | 加入重复人物 ID、无效职业引用 | 内容校验失败并定位字段 | M0 |
| T03 | 长行动中途跨寿终、完成时刻恰等于死亡时刻、或同tick先有其他致死事件 | 停止后续收益，结束一次，记录实际已发生部分 | M0/M1 |
| T04 | 连续执行十次短劳动/学习/休息 | 时间/有限资源按契约消耗，不无限免费增长 | M1 |
| T05 | 帮助 NPC 后重建地图、切换观察视角 | 人物 ID 与关系保持 | M1 |
| T06 | 母亲改行、节令完成后立即存读档 | 职业、节令次数和相关家庭状态保持 | M1 |

测试应经真实 ActionCommand 入口验证路线可达性，不能只直接调用“升官”“获得进士”等内部函数。内部函数可用于建立测试状态，但必须区分准备步骤和被测行为。

### 4. 确定性与随机性的共同验收

固定种子用于复现，不用于消灭随机。一个测试包记录：引擎精确版本、模拟版本、内容哈希、世界种子、全部随机流起始状态、命令序列、已接受外部提案、预期状态摘要。

随机概率由“前置条件正确”和“权重实现正确”先保证，再在足够样本上检查分布。不要在10局里要求某个5%事件必须刚好发生一次。概率测试使用明确置信或容差规则；如没有足够样本，仅报告观察结果，不能断言分布无偏。

M0先建立少量定向用例；M1/M2 的相关 PR 使用必要的固定种子与边界案例；M3 具备无界面跑完一生能力后，先跑约100局发现系统问题，再视性能与风险扩展到约1000局。数量是可调整的测试预算，不是统计保证。失败时保存最小命令序列、失败种子和状态片段。

状态摘要只包含模拟真相，排除时间戳、截图、窗口尺寸等非决定字段。字典排序、ID生成、候选遍历和浮点运算应在固定平台/版本下明确；若跨平台不保证位级一致，明确支持边界。

### 5. 内容与叙事的可测质量

| 指标 | 定义 | 首个完整版本的目标 |
|---|---|---|
| 引用合法率 | 正式包中ID、演员、物品、条件和效果合法 | 正式入库内容全部通过检查 |
| 触发覆盖 | 每条正式事件至少存在一组合法触发状态 | 100%有fixture；不等于每局都能遇到 |
| 因果可追溯 | 重要事件能找到直接原因或明确的环境/偶然来源 | 规定的关键事件全覆盖 |
| 后续处理完整 | 延迟项能执行、取消、替换或过期 | 定向场景无永久悬挂和重复结算 |
| 选择差异 | 重要选项产生不同可观察状态或机会 | 每条重要事件人工/Agent审查，不以文案差异代替 |
| 年龄/路线覆盖 | 各成长阶段和三条路线都有可做之事 | 完整人生可持续推进 |
| 重复感 | 相似事件连续出现和同台词高频复用 | 先记录基线，按试玩反馈设冷却与组合规则 |
| 普通人生表达 | 非显赫人物回望是否包含具体关系与经历 | 试玩者可辨认本局独特细节 |

所有“0错误”都只指已经执行并记录的测试集合。发布后仍保留错误收集与新种子回归机制。

### 6. 试玩脚本

至少准备三种体验任务：继续求学、拒绝读书走手艺、留乡照护并中途转向。另选相同seed的不同选择、不同seed的相同意图，比较变化是否能解释。

不要在试玩开始前告诉玩家所有设计答案。结束后收集：

1. 哪一次决定改变了后来的一件事？能说出原因吗？
2. 哪个人物让你觉得他有自己的生活？证据是什么？
3. 什么时候觉得只是机械刷数值、等待或重复点击？
4. 有想做却完全没有入口的行动吗？无法做时，解释是否合理？
5. 失败之后是否仍想继续？如果不想，原因是什么？
6. 这次结局有哪些细节属于你，而不是谁都能套用？

试玩报告保留用户原话与观察事实，把设计者解释另列。Agent可以分析反馈，不能编造真人反馈或自行给出“玩家满意度100%”。

### 7. 性能与发布验收

先测现有基线，记录CPU/GPU/内存、系统、分辨率、人口、事件数、存档体积和关键场景。可初步以目标桌面上稳定接近60FPS、普通模拟步骤不造成明显卡顿、保存加载可接受为体验目标，再按测量制定明确P95预算；不能用未测的硬件承诺结果。

性能优化前后回放相同输入，确保事实一致。人物分层模拟与日志压缩都要保持重要信息，不能为加速丢债务或将死者当普通远方NPC。

发布候选需包含：实际可启动的平台产物、精确commit/引擎/内容版本、变更日志、存档兼容与回退方案、已知问题。CI状态属于该提交；旧提交全绿不代表新提交通过。没有平台构建和实际启动证据，就只报告源码交付。

### 8. 测试文件与数据隔离

真实存档属于用户的世界。测试使用独立路径，由测试入口注入并打印可核对的位置；worktree与user://并非天然隔离。已有 --fresh 会清除三个槽与旧单文件，隔离前不可使用；普通启动也可能读写档，所有游戏运行都须先证实隔离。

## 共同设计约束

- 世界只有一条模拟时间；表现动画可以独立平滑运行，不能改变经济、年龄或随机结果。
- 所有核心人物有稳定ID、真实生命周期、关系和记忆；切场景与读档不重建人生。
- 长行动跨过到期事项时按序结算；同tick死亡判定优先于主体任务完成收益，不能死后发奖。
- 随机必须先通过时代、年龄、地点、演员、资源与事实条件；约定到期事项不能靠抽奖才发生。
- 内容先结构后文案，有拒绝、延期、失败、死亡/离乡和过期处理；任何关键回望都追溯事实。
- NPC有自己的目标和选择，可以拒绝玩家。重要过去不可为了新剧本改写。
- 先采用开发期AI生成候选内容，经校验和模拟后入库；游戏离线可玩。运行时AI无权直接改钱、改关系、改死亡或改历史。
- 同种子重放要求引擎、模拟、内容版本一致，并保存随机状态；不承诺跨版本天然一致。
- 保留用户未提交修改和真实存档，不强推覆盖历史。公开发布、自动合并和付费服务按已有明确授权执行。

请现在从M0-01开始，用可核验的工作结果推进；每次完成一个小任务都把代码或文档提交并push，然后记录当前状态和下一步。
