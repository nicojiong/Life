# M1-04d 验证证据：旧档迁移 fixtures

- 日期：2026-10-24
- 任务：M1-04（切片 d），审计 A02
- 基线：`c0e11dd`（M1-04c 分支）

## 1. 目的

证明「没有新字段的旧存档」不是崩溃，也不是假装完整：能读、每个缺失字段有**明确且可解释的默认**，并且下一次保存会升级到 `schema_version=2`。

## 2. Fixture

`tests/fixtures/save_v1.json` 是一份 v1 存档（21 岁、3 亩地、自耕农、已婚一子、欠李婶米、`origin_flags=["农家","乡村"]`）。它**故意不含**：

`schema_version`、`father_trade`、`mother_temper`、`women_rank`、`scenes_done`、`child_last`、`time_scale`、`parent_dead`、`parent_death_year`。

## 3. 迁移规则

| 缺失字段 | 默认来源 | 理由 |
|---|---|---|
| `father_trade` | 由 `origin_flags` 经 `_father_trade_for()` 推导 | 旧档没有记录父亲行当，但出身还在，推导比随机或沿用内存值更接近事实 |
| `mother_temper` | `"和"` | 中性值，不凭空造出一个严厉或病弱的母亲 |
| `women_rank` | `0` | 宁可能力归零，也不凭空给一个从未发生过的绣坊 |
| `scenes_done` | 空 | 旧档没有节令记录，宁可当年可重复，也不假装过过 |
| `time_scale` | `1.0` | 基准流速 |
| `parent_dead` | `{false,false}` | 旧档无法区分"已故"与"字段缺失"，按在世处理并保留补生成（已知妥协） |

## 4. 断言

```
[VERIFY] PASS save_migrates_v1 upgraded_to=2.0
[VERIFY] SUMMARY pass=13 fail=0 failed=[]
```

流程：

1. 把 fixture 写进隔离目录的 `user://fusheng_save_1.json`；
2. `_load_game()`；
3. 断言：读取成功、`name=李守拙`、`money=3456`、`father_trade=="农"`（由「农家」出身推导）、`mother_temper=="和"`、`women_rank==0`、`time_scale==1.0`、`save_schema_seen==1`；
4. `_save_game()` 后重新解析文件，断言 `schema_version==2` ——**迁移在下次保存时落地**。

## 5. 第一版为什么会红

第一次跑 `save_migrates_v1` 是 FAIL：`father_trade` 读档后既不是「农」也不是旧值，而是**上一次测试残留在内存里的值**。

原因：`_load_game()` 用的是 `d.get("father_trade", father_trade)`——"缺字段就保留当前内存值"。对一份刚开局的内存状态来说，这等于把**这一次随机的父亲**塞进了别人的存档。改成按 `origin_flags` 推导后通过。

这条断言因此不只是测"能不能读"，它测的是"读旧档会不会把别人的世界拼到你的存档上"。

## 6. 未覆盖

- 旧档的父母仍会被补生成（`schema_version < 2` 分支），无法区分当年是否已故。
- 没有真实的用户旧档样本（fixture 是手写的），也没有多版本链（v1→v2→v3）。
- RNG、NPC 关系、事件队列不在存档内，`M1-04` 的对应验收项仍依赖 M1-03 与 M1-01。
