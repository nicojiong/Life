# M1-03b 验证证据：事实日志与起因

- 日期：2026-10-24
- 任务：M1-03（切片 b），审计 A02 / §6
- 基线：`91ab293`（M1-03a 分支）

## 1. 问题

游戏里发生的事只有两种去处：一条会淡出的 toast，或者直接改写某个数字。没有地方记录"**谁在什么时候、因为什么**"。

后果很具体：

- 墓志只能拼几个当前字段，写不出"他为什么变成这样"；
- 调试时只能看终值，无法回答"这 18 点声望是哪来的"；
- 规划要求的"回望必须追溯事实"无从执行。

## 2. 做法

```gdscript
var facts: Array = []          # 上限 240 条，超出丢弃最旧
_log_fact(kind, cause, data)   # 时间 / 类型 / 起因 / 附加数据
```

接入点（本轮）：

| 事件 | kind | cause |
|---|---|---|
| 解试通过 / 落第 | `exam` | `jieshi_pass` / `jieshi_fail` |
| 省试通过 / 落第 | `exam` | `shengshi_pass` / `shengshi_fail` |
| 说成亲事 | `marriage` | `meiren` |
| 父母过世 | `death` | `old_age` |
| 年度随机事件 | `event` | `year_end`（附事件 id） |

日志入库（schema 4 → **5**）。

## 3. 断言

```
[VERIFY] PASS facts_have_causes kinds=["event", "exam"]
[VERIFY] SUMMARY pass=18 fail=0 failed=[]
```

检查三件事：

1. 触发一个事件 + 记一条考试事实后，日志至少两条；
2. **每条都有非空 `kind` 和 `cause`**（不允许"不知道哪来的事"）；
3. 时间戳 `t` 单调不减。

## 4. 为什么只接了五个点

日志的价值取决于它是否**可信**，不取决于条数。先接五处、保证每条都有起因，比接三十处然后一半是 `cause: ""` 更有用。

## 5. 未覆盖

- 还没有查询接口：墓志仍不读日志，调试也只能 `print(facts)`。
- 没有 `cause_ids` 的因果链（现在只有单层 `cause` 字符串，不是引用别的事实 id）。
- 容量上限会静默丢弃最旧的记录，没有"被丢弃"的标记。
- 日志没做压缩，长跑可能撑大存档（240 条 × 小字典，暂未测体积）。
